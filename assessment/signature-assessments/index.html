Signature Assessments

Signature assessments are the formal, high-stakes assessment events distributed across the program. Each is a culminating instance of a recurring assessment type — it represents that type at its most consequential, typically involving real artifacts, peer or faculty audience, and no scaffolding.

Five formal, high-stakes signature events are distributed across the program, though not evenly: two converge on the same course (CIS 400), and one no longer fits inside the two-year core at all.

Code Archaeology Milestone

CIS 200 — Programming Fundamentals (Y1 Spring)

Students investigate an unfamiliar, moderately complex codebase — written in languages they know — to explain its behavior, identify sources of unexpected behavior, and propose a repair. This is the first unscaffolded instance of the Code Archaeology recurring type, building on the informal code-reading groundwork CIS 116 already seeds (SLO 4: “read, interpret, and modify existing computer programs”).

Code Archaeology does not end at CIS 200. It recurs and deepens throughout the program (see Recurring Assessment Types), but this milestone is the first formal, evaluated instance.

Evidence generated: Analyze Computational Systems; Maintain Software Systems

Data Investigation

CIS 260 — Foundations of Relational Databases (Y1 Spring)

Students identify a question they want to investigate, acquire or are given a novel dataset, and conduct a complete investigation: schema design, query strategy, statistical summarization, and interpretation. The investigation is documented and presented.

This is the formal instance of the Data Investigation recurring type and anchors CIS 260’s evidence for the Data and Information domain. (This single 1-credit course carries content dense enough to flag — see the course’s existing density note in resources/reference/degree-maps/cs.md.)

Evidence generated: Investigate Questions with Data; Manage Data Resources; Represent Information

Design Review

CIS 400 — Object-Oriented Design, Implementation, and Testing (Y2 Spring)

Students present a system design — algorithm selection, data model choice, and architectural tradeoffs — to a panel of peers and faculty and defend their choices under critique. The defense must address correctness, performance, human-centered concerns, and ethical implications.

Homed at CIS 400. The algorithmic content this event needs (graph algorithms, shortest-path/MST tradeoffs) lives in CIS 300’s graph unit — but the defense format this assessment actually needs (present to a panel, defend under critique) has no such event in CIS 300’s drafted content. CIS 400 is the confirmed host instead: its “Confirmed Design Intent” section already commits to “a live walkthrough and architecture defense” as the course’s actual verification mechanism, not spec-compliance checklists. This is the same convergence already flagged in resources/design-log.md’s 2026-07-15 pedagogy-chapter entry.

Design Review is the highest-stakes instance of both the Design Brief and the Technical Explanation Task recurring types.

Evidence generated: Design Software Systems; Develop Abstractions; Evaluate Algorithmic Solutions; Communicate Technical Information; Evaluate Ethical Implications

Team Software Project

CIS 400 — Object-Oriented Design, Implementation, and Testing (Y2 Spring)

Students collaborate on a shared software product — building toward the historical-archive real-world asset, in small teams with rotating scope — taking it from requirements through implementation, testing, and deployment, with an individually-written responsibility retrospective as part of the assessed work.

Worth naming plainly: the course sequence consolidates the entire team project into a single course, CIS 400, which now hosts both this and Design Review above — two signature events converging on one course rather than staying spread across the program. This is confirmed intent, not a gap: see cis-400.md’s “Confirmed Design Intent” section and resources/design-log.md’s 2026-07-13/07-15 entries.

This is the primary evidence context for the Professional Practice domain and generates sustained evidence for collaborative, implementation, maintenance, and verification competencies.

Evidence generated: Collaborate on Software Teams; Implement Software Solutions; Verify Software Quality; Maintain Software Systems; Evaluate Ethical Implications; Reflect on Professional Growth

System Integration Project

Year 3–4 program capstone (CIS 598 / CIS 643 / DEN 591) — not inside the two-year core

Students design, build, deploy, and validate a multi-component system for real users. The project includes formal requirements gathering, acceptance testing with actual users, and a blameless postmortem. Students prepare an employer-facing competency report drawing on their full Crystalis evidence record.

This event sits outside the two-year core. resources/reference/spiral-threads.md’s Sociotechnical re-homing table places the full team-level “blameless postmortem” REFLECT pass at the Year 3–4 program capstone, explicitly not inside the two-year core — and this assessment’s other defining features (acceptance testing with real users, an employer-facing competency report) fit that same later, whole-degree-culminating point better than a two-year-core event. CIS 400 is the core’s own capstone, but it is deliberately scoped smaller (team project + architecture defense, no external-user acceptance testing or postmortem) — see this page’s Team Software Project and Design Review entries above for what CIS 400 actually carries.

This is the program’s culminating assessment event and generates evidence across all six competency domains.

Evidence generated: All domains; final evidence anchor for Adaptation-level claims

Three of the five events map onto the two-year core (Code Archaeology → CIS 200, Data Investigation → CIS 260, and CIS 400 hosting both Design Review and Team Software Project); System Integration Project’s move to the Year 3–4 capstone is a real scope decision that should be confirmed explicitly with faculty, not just inherited from this migration pass.
