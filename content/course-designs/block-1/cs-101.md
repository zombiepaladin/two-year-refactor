## CS-101 — Imperative Programming

**1 credit**

### Working description

State, mutation, control structures — the sequence-of-steps-that-change-things paradigm. Opens with a tightly-scaffolded H5P widget (translate sheet music into an ordered sequence of QBASIC `SOUND` commands) as the first concrete embodiment of "imperative = an ordered sequence of steps, each producing an effect before the next begins," then moves rapidly into real, modern-language practice: **Python is the primary produce language**; Go and C are used for **comparative reading** of the same constructs (variables, control flow) across languages a student is likely to encounter. Lists at shallow depth. Mutable variable assignment is introduced as an explicit paired contrast with CS-102's immutability. The same H5P widget returns twice more, for different concepts: its `GOTO` capability opens a short history-of-structured-programming discussion (Week 3), and a multi-voice/parallel-sequence mode supplies a first, deliberately simple, no-shared-state concurrency seed (Week 7). A new H5P drag-and-drop widget introduces the stack/heap as a **notional machine** (Week 6), paired with a VS Code debugger-visualization plugin as the "real tool" bridge; Week 6's worked example is a recursive function, explicitly cross-referenced to CS-102's Week 6 (same function, elegance/composition angle rather than memory-trace angle). Week 7's concurrency seed now also includes a bounded, surface-level glimpse of *why* shared state is hazardous under concurrency — not just that it's deferred. (Codes are placeholders.)

**Read vs. produce balance:** the block's cognitive frame is still READ (per `content/core-design/blocks/block-1-read.md` — "the first encounter with code is reading it"). Every week below now has a real produced component (per explicit instruction), but production stays uniformly small/scaffolded (translate a melody, a tiny variable exercise, a GOTO-to-structured refactor, a notional-machine sketch); the larger, more open-ended component each week is reading and explaining unfamiliar or cross-language material (stack traces, git history, someone else's code, a second language's syntax for the same idea). The ratio shifts, not the frame.

**HTML/CSS/declarative content has been removed from this file.** It was previously drafted here in error; it is already fully owned by CS-106 (`content/course-designs/block-2/cs-106.md` — semantic HTML/CSS, DOM, declarative-model naming, async/event-loop, browser-as-mini-OS). See the 2026-07-09 (follow-on) design-log entry for the resolution.

## Learning outcomes

- Write and explain small imperative programs using variables, mutable assignment, and basic control structures (sequence, iteration, selection), primarily in Python, recognizing the same constructs in Go and C. (SD.2, CR.1)
- Translate an external notation (sheet music) into an ordered sequence of commands; extend that translation to multiple independent sequences with no shared state between them. (CR.2, SD.2)
- Contrast mutable assignment (this course) with immutable binding (CS-102) as two different answers to the same question: does a name's value change over time? (CR.2)
- Explain, at a high level, why structured control-flow constructs (loops, conditionals) replaced unstructured `GOTO`-based flow, and refactor a small GOTO-based sequence into structured form. (CR.1, SD.2)
- Draw a simplified ("notional machine") model of a program's stack frames, heap allocations, and execution pointer at a specified point in a function-call sequence, and relate that model to what a real debugger tool shows. (CR.2, CR.1)
- Read a stack trace or compiler error produced by a common mistake and explain, in your own words, what went wrong — recognizing the same class of error's different surface in Python vs. a compiled language. (CR.1)
- Read git history (log/diff/blame) to reconstruct what changed in a small codebase and why, including using blame to find when a bug was introduced. (PP.1, light touch)
- Use an AI tool to explain an unfamiliar snippet, then verify that explanation against the program's actual behavior. (PP.2, light touch)
- Produce both inline comments and a standalone explanatory document for a piece of code. (HCP.4)
- Name that more than one computational model exists — imperative vs. functional (paired with CS-102), and sequential vs. many-independent-sequences-at-once — and give a concrete example of each. (CR.1, CR.2)

## Language decision (stated plainly, per instruction)

**Python is CS-101's primary produce language.** Every produced exercise (sequence-of-statements, mutable variables, loops/conditionals, GOTO-refactor, notional-machine walkthroughs) is written in Python. **Go and C appear as comparative reading material only** — the same construct shown side-by-side in a second/third syntax, to build early, low-stakes exposure to syntactic variation across imperative languages a student is likely to encounter, without requiring production fluency in either. This is consistent with the design log's Round 41 language-agnostic-core-plus-certificates principle: reading exposure to multiple languages' syntax is not the same claim as "the core teaches deep fluency in five languages," and doesn't compete with the certificate model (Python/C/Go remain plausible certificate candidates for later deep fluency). See the design-log follow-on entry (2026-07-09) for the full reconciliation of this point against last session's unresolved "Python/Java/Elixir/Prolog/Go" flag.

## Concurrency seed: reasoning and forward spacing

(Unchanged from the prior session's design, relocated to Week 7 — see the week-by-week map above for the updated slot.)

The Week 7 content is the concrete, experiential vehicle for a **Go-goroutine-inspired** concurrency concept: lightweight, independently-scheduled sequences of steps, introduced **without shared mutable state**, so race conditions, locks, and shared-memory hazards are explicitly out of scope until Block 8. This is a concept-level seed, not Go syntax instruction.

**Relationship to CS-103's process seed (same block) — complementary, not conflicting.** CS-103 grounds a *formal/OS-level* view: your whole program is one process the OS schedules (single-threaded, for now). CS-101's widget grounds a *concrete/experiential* view at a different grain: *within* a program, you can describe several independent sequences that each make progress "at once." These operate at different levels and do not contradict each other — the distinction between them is exactly what gets formalized at B8 (cooperative/green threads running inside a process vs. OS-scheduled preemptive threads/processes). **CS-103 is now built** (`content/course-designs/block-1/cs-103.md`, Week 6) with exactly this cross-reference in place.

**CS-102 companion pass — firmly adopted this session (no longer a recommendation).** `content/course-designs/block-1/cs-102.md` now has this as real, built content at its own Week 7: functional programming's immutability makes "nothing is shared" the *default*, not an engineered simplification. CS-102's Week 7 makes this the explicit paired contrast to CS-101's Week 7 — "CS-101 had to *decide* not to share anything between voices to keep it simple; in CS-102, nothing is *ever* shared between pure functions, so this is just how the model already works" — and extends it to the new shared-memory glimpse below: CS-102 is where students see *why* immutability sidesteps the hazard CS-101 just demonstrated, by construction, with no shared mutable counter to race over in the first place. This dovetails with Week 2's mutable/immutable pairing point — both are facets of the same imperative-vs-functional contrast, at different points in the block.

**Shared-memory surface glimpse — new this session, revises the spacing judgment below.** Week 7 no longer stops at "nothing is shared, full stop" — it now poses (without resolving) the question of what goes wrong if something *were* shared, via a hand-traced lost-update example. This is a genuine scope addition, not a reframing, so the B1 row of `content/core-design/threads/thread-computational-models.md` and the spacing judgment immediately below have both been revised to account for it.

## Recursion: one function, two angles (cross-referenced with CS-102, same week)

Week 6's stack/heap notional-machine example uses a recursive function so that recursion and memory-model tracing are taught together rather than as two unrelated topics. CS-102's own Week 6 (see `content/course-designs/block-1/cs-102.md`) uses the *same* function to teach the complementary angle: not what recursion does to the call stack, but what it lets you express — a solution defined in terms of itself, with no mutable accumulator or loop counter. Framed explicitly to students as: "you'll see this exact function twice this week, in two courses, for two reasons — CS-101 asks what happens in memory; CS-102 asks why this is a natural way to describe the problem." This is deliberate connective tissue, not duplication.

## Stack & heap notional machine: reasoning, tool bridge, and forward spacing

**Why "notional machine" is the right frame, not a new coinage.** This term is already load-bearing in the design log for the program's broader layered-abstraction philosophy (People → Requirements → … → Processes → Memory → Files → Networks → Users). The stack/heap widget is a zoomed-in instance of the *same* idea, applied to a single program's execution: a deliberately simplified model that preserves what matters pedagogically (call frames stack and unwind; the heap persists independent of calls; an execution pointer moves through it) while dropping real-implementation fidelity (actual register allocation, real memory addresses, compiler-specific frame layout, garbage-collection mechanics). Both the widget and the class discussion must say this out loud — it is explicitly not a claim about how any specific language's runtime actually works.

**Relationship to CS-103 — a real ownership question, resolved the same way as the concurrency seed.** CS-103's stub already names "the stack and the heap (stack frames for calls/recursion; heap for dynamic allocation)" as its content, and already has a committed, graded assessment row: *System Analysis Task — trace stack/heap state through a function call sequence — Analyze System Behavior (SI.1)*. Introducing a new CS-101 widget that both demonstrates and assesses stack/heap risks silently duplicating that claim. Resolution adopted here, mirroring the CS-101/CS-103 concurrency-seed pattern from the prior session: **CS-101 owns the concrete/experiential, formative first encounter** (the H5P notional-machine widget + the VS Code debugger walkthrough, assessed only as a Tier-1 automated/formative check mapped to CR.2 — see the Competency Assessments section); **CS-103 continues to own the formal, graded assessment** (System Analysis Task, SI.1) — at greater systematic depth (a longer call sequence), now also extended to register-level tracing. **CS-103 is now built adopting exactly this split** (`content/course-designs/block-1/cs-103.md`, Week 6), reusing the same widget/VS Code tool as its vehicle. See `resources/reference/block-inventory.md` for the resolution note.

**The VS Code plugin is a bridge, not a separate topic.** It appears in the *same* week (6), applied to the *same* worked example, specifically to show students that the H5P notional machine and a real tool's own (still simplified) visualization are related but not identical — the widget teaches the concept; the plugin previews what a professional tool gives you for the same concept.

**Forward spacing:** introduced B1 (CS-101 concrete pass, same week as CS-103's formal pass — 0-week gap, same block, deliberate); the concept lies dormant (not independently re-taught) until B8 (CS-210), where shared-vs-isolated memory becomes load-bearing for distinguishing threads from processes from green threads. That's roughly a full academic year of gap for a foundational memory-model concept that the concurrent-models comparison cannot be reasoned about without. Same judgment as the concurrency seed's B4→B8 gap: acceptable for a systems concept if CS-210 explicitly recalls the B1 model rather than assuming retention.
