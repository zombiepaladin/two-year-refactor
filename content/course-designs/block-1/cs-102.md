## CS-102 — Functional Programming

**1 credit**

### Working description

Functions as values, composition, immutability, basic recursion — the describe-the-result-as-composed-transformations paradigm. Paired solve-it-both-ways exercise with CS-101 names the idea of more than one computational model. Immutable binding is taught as an explicit, same-week paired contrast with CS-101's mutable variable assignment (Week 2). Basic recursion (Week 6) uses the *same* worked function as CS-101's Week 6 stack/heap notional-machine widget — CS-101 asks what recursion does to the call stack; CS-102 asks what it lets you express, with no mutable accumulator. A same-block concurrency companion pass (Week 7) contrasts CS-101's *engineered* "nothing is shared" simplification with functional immutability's *intrinsic* answer to the same question, and sharpens the new shared-memory hazard glimpse CS-101 introduces the same week: immutability avoids the hazard by construction. (Codes are placeholders.)

**Read vs. produce balance and language decision, stated plainly (mirroring CS-101's discipline):** **Python is CS-102's primary produce language too** — the same base language as CS-101, disciplined to a functional subset (no reassignment once a name is bound; compose small functions; use recursion instead of loops with mutable counters). Using the *same* language as CS-101, taught under different rules, is deliberate: it isolates the *paradigm* as the variable a student is comparing, not the language, which sharpens the Week 5 "more than one computational model" checkpoint. **Honest caveat:** Python does not enforce immutability at the language level — a CS-102 "immutable" binding is a discipline/convention within the course, not a compiler-enforced guarantee. **JavaScript is used as comparative reading only** (arrow functions, `const`, `.map`/`.filter`/`.reduce` chains) — chosen deliberately over Elixir, specifically to preserve Elixir's *unfamiliar-paradigm* framing for B3's Code Archaeology pass (`recurring-assessments.md`: "unfamiliar paradigm (Elixir/Chrysalis)" at B3, CS-107). Showing Elixir here first would blunt that later novelty. This is a new, explicit decision this session — flagged for confirmation alongside CS-101's parallel Python/Go/C decision.

## Learning outcomes

- Define and apply functions as values, primarily in Python, recognizing the same idea (arrow functions) in JavaScript. (SD.2, CR.1)
- Compose small functions into larger ones; work with simple immutable lists (map/filter conceptually). (CR.2, SD.2)
- Contrast immutable binding (this course) with mutable assignment (CS-101) as two different answers to the same question: does a name's value change over time? Name Python's honest limitation here (discipline, not enforcement) against JavaScript's `const` (language-enforced). (CR.2)
- Write and reason about basic recursion (countdown, sum-a-list, simple factorial-style cases); explain the *same* recursive function CS-101 traces through the call stack in terms of what it lets you express, without a mutable accumulator. (CR.2, SD.2)
- Explain why independent, pure computations can run in any order — or "at once" — safely, with no coordination needed, and why that's a *consequence* of immutability rather than an engineered rule (contrast with CS-101's Week 7). (CR.2, CR.1)
- Explain, at a conceptual level, why a shared mutable counter can lose an update under concurrency, and why immutability avoids that hazard by construction (paired with CS-101's Week 7 hand-traced example). (CR.1)
- Read a short unfamiliar functional program and explain what "no valid output for this input" looks like, contrasted lightly with CS-101's crash-mid-sequence framing. (CR.1)
- Read git history (log/diff/blame) on a functional-style codebase to reconstruct what changed and why. (PP.1, light touch)
- Use an AI tool to explain an unfamiliar functional snippet, then verify against actual behavior using input/output asserts. (PP.2, light touch)
- Produce both inline comments and a standalone explanatory document for a piece of functional code. (HCP.4)
- Name that more than one computational model exists — functional vs. imperative (paired with CS-101) — and give a concrete example of each. (CR.1, CR.2)

## Prerequisites and standalone-extractability

No CS prerequisites — co-scheduled with CS-101/CS-103/MATH-101 as parallel B1 courses, not sequential to them. Per the same service-course principles applied to CS-101 (service-extractability decays with block depth, not yet formally analyzed for this course either): CS-102 is likely *less* independently extractable than CS-101, since several of its strongest moments (the Week 5 paired checkpoint, the Week 6 recursion cross-reference, the Week 7 concurrency companion pass) are explicitly built as same-week counterparts to CS-101 content and would need re-authoring as standalone material to work outside the pairing. The core functional-programming skills (functions as values, composition, basic recursion) would likely still transfer to a standalone "intro to functional thinking" context, but the distinctive design of this course — teaching functional style as a *contrast* to something else being learned simultaneously — is inherently paired. Flag before relying on this for a service-course conversation.
