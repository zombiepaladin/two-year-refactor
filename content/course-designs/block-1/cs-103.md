## CS-103 — Computational Representation

**1 credit**

### Working description

Boolean logic, number systems, bitwise operations — applied counterpart to Discrete Math Logic & Sets (MATH-101). Opens with Babbage's Difference and Analytical Engines as historical grounding — number representation is a *design choice* (Babbage's mechanical engines computed in decimal), motivating why electronic computers standardized on binary instead. Binary representation of primitives (integers, characters) follows directly, alongside a light home for the representation/hiding security question. A simplified 8-bit float format is worked by hand. Registers and the basic register-transfer model of how primitive operations are actually carried out are introduced as the programmer-facing ALU/register level — absorbing the programmer-facing part of computer architecture, alongside the already-established stack/heap memory model (stack frames for calls/recursion; heap for dynamic allocation). Execution-model seed: a running program is a PROCESS the operating system schedules (single-threaded for now) — the grounding the concurrent models will need later, cross-referenced explicitly with CS-101's Week 7 concurrency seed. HDL/FPGA intentionally not produced.

**Relationship to CS-101 — same tools, deeper/formal pass, resolved this session.** CS-101's Week 6 introduces an H5P drag-and-drop notional-machine widget (stack/heap/execution-pointer) and a VS Code debugger-visualization plugin, at concrete/formative depth, using a recursive function shared with CS-102's Week 6. This file adopts the split proposed there: **CS-103 owns the formal, graded assessment** for stack/heap (already committed below as a System Analysis Task row), reusing the *same* widget and tool at a longer, more systematic call sequence, and **extends the same widget** to also cover register-level state (see Weeks 4–5). CS-101's file is not re-edited here; this is confirmation that the split lands as proposed.

## Learning outcomes

- Explain why number representation is a design choice, using Babbage's decimal mechanical engines as a contrast to binary electronic computation, and articulate why binary won out for electronic hardware (reliability of two-state signals). (CR.1)
- Represent integers and characters in binary; perform basic bitwise operations. (DI.1, SD.2-adjacent but not separately claimed)
- Encode and decode values in a simplified 8-bit floating-point format by hand (sign/exponent/mantissa), and explain the sign/exponent/mantissa roles by analogy to (not identity with) real floating-point formats. (DI.1, CR.3)
- Construct and evaluate truth tables, predicate-logic statements, and basic set proofs, paired with MATH-101's treatment of the same material. (CR.3)
- Explain, at a register-transfer level, how a basic arithmetic operation is carried out using registers — what a register is, and what "load, operate, store" looks like for a single instruction. (CR.1, SI.1)
- Trace stack frames, heap allocations, and now register state through a function-call sequence, using the same notional-machine widget and VS Code tool introduced (at lighter depth) in CS-101. (SI.1)
- Explain that a running program executes as a single OS-scheduled process (single-threaded, for now), and connect this explicitly to CS-101's within-program concurrency seed as a complementary, not competing, view. (CR.1)
- Read git history (log, diff, blame) to reconstruct what a collaborator changed in a codebase and why. (PP.1)
- Articulate, at a light/conceptual level, how a representation choice affects what can be hidden or obscured. (HCP.3)

## The 8-bit float format: proposed layout and rationale

A specific proposal, not left vague, per instruction: **1 sign bit + 4 exponent bits (bias 7) + 3 mantissa bits**, with an implicit leading 1 in the mantissa (normalized form `1.mmm × 2^(e-7)`), mirroring IEEE 754's structure at a scale small enough to work by hand in a 1-credit course:

- **Sign (1 bit):** 0 = positive, 1 = negative.
- **Exponent (4 bits, bias 7):** stored value 0000–1111 (0–15); actual exponent = stored − 7, so usable actual exponents run roughly −6 to +7 once the all-0 and all-1 patterns are reserved (all-0 for zero/subnormal, all-1 for infinity/NaN — mirroring IEEE 754's reserved patterns at toy scale, so the "reserved values exist" idea transfers even though this format is not a real standard).
- **Mantissa (3 bits):** fractional bits after an implicit leading 1, giving 8 representable fractions between each power of two.

Worked example to include in the widget/materials: represent 3.5 → `3.5 = 1.75 × 2^1` → sign 0, actual exponent 1 → stored exponent `1 + 7 = 8` = `1000`, mantissa `.75` = `110` (0.75 = 0.110₂) → full encoding `0 1000 110`.

**Why this layout, not another:** 4/3 exponent/mantissa split gives students a workable dynamic range (roughly 2⁻⁶ to 2⁷, enough to feel like "a real range" rather than a toy that only represents values near 1) while keeping the mantissa small enough that decode-by-hand stays tractable in a single class session. **Notable, worth stating to students as a hook:** this 1-4-3 layout is structurally similar to real 8-bit float formats used in modern ML accelerator hardware (e.g., the E4M3-style FP8 formats used for quantized neural-network computation), so this isn't a purely invented toy — it's a simplified instance of a format with real, current relevance. **This specific layout is my design proposal for this session and should be treated as a confirmable decision, not a settled fact** — an alternative (e.g., 1-3-4, favoring mantissa precision over range) is equally defensible; flagged for confirmation.

## Registers and the VS Code tool: a capability flag, not an assumption

The user asked that CS-103 "reuse the H5P notional-machine widget (extended) and/or the VS Code plugin" for register-level state, and asked explicitly that I check whether the VS Code plugin's actual capability supports this rather than assume it does. **I cannot confirm this from the materials available to me, and I'm flagging it rather than assuming a clean answer:**

- The H5P widget extension (a register lane added to the existing drag-and-drop stack/heap panes) is straightforward in principle — it's the same authoring pattern as the existing widget, just a new visual lane, and I'm treating that part as low-risk.
- The **VS Code debugger-visualization plugin bridge is a real open question.** CS-101's tool bridge (Week 6) works because it's debugging a *Python* example, and typical Python debugging in VS Code (via `debugpy`) shows Python-level stack frames and variables — it does not meaningfully expose general-purpose CPU registers, because CPython execution doesn't map to visible hardware registers in a pedagogically clean way. A register-level *live tool* view is much more plausible when debugging a small **compiled C example** via VS Code's C/C++ extension (GDB/LLDB register views are a real, common feature there) — which is workable here since C is already a read-comparison language in CS-101, so students have seen its syntax. **This means Week 5's tool bridge may need to switch the debugging target from Python to a small C example specifically for this one week, which is a bigger ask than CS-101's Week 6 (same language throughout).** I have not confirmed the exact plugin the user has in mind or its actual feature list. Recommend confirming with whoever owns the actual tool before committing to a live register-view demo; if it doesn't pan out, the H5P widget extension alone still delivers the core content, just without the "real tool" bridge for this specific topic.

## Density — an honest read, not forced

This is a substantially denser build than CS-101 or CS-102 relative to what existed before it: the prior stub had essentially zero week-level content, and this session adds Babbage history, binary-primitive representation, an 8-bit float format worked by hand, two full weeks of register/ALU content, the (already-committed but now-expanded) stack/heap formal assessment, a process-execution seed, and a formal git-history capstone — eight substantive items competing for eight weeks, plus the pre-existing boolean-logic/MATH-101 pairing.

**I do not think this fits comfortably without the compression choices already built into the map above**, specifically:
- Babbage's history is deliberately *not* a full week — it's a bounded aside inside Week 1, the same treatment CS-101 gives Dijkstra/GOTO. If faculty want it as genuine standalone content (more than a class-session hook), something else has to move.
- The 8-bit float's *encoding* direction is scoped as a scaffolded stretch goal, not a fully independent baseline skill — full by-hand encoding fluency for all students would likely need more than the single Week 3 allotted here.
- Week 7 is explicitly consolidation, not new material — this is the release valve that makes the rest of the map plausible; if register/ALU content (Weeks 4–5) turns out to need more time in piloting, Week 7 is the natural place to absorb that overflow, at the cost of losing the synthesis week's own value.

**Registers (Weeks 4–5) are the single highest-risk item in this file** — it's the most genuinely new, hardware-adjacent content, it depends on the still-unconfirmed tool-capability question above, and it has no prior treatment anywhere in the design log to calibrate difficulty against (unlike, say, recursion or git history, which have precedent elsewhere in the program). If piloting shows two weeks isn't enough — or is too much — Week 7's synthesis slot is the recommended place to absorb the difference, since it's consolidation rather than new content and can flex without displacing anything else.

**Net honest assessment:** the map above is a workable draft, not a confirmed-comfortable fit. Of the three B1 CS courses built this session, CS-103 is the one I'd most want faculty to pilot before treating as stable.
