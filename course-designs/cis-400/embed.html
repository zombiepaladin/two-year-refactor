CIS 400 - Object-Oriented Design, Implementation, and Testing

CIS 400 is being reimagined as a mid-level capstone course, where students use what they have learned in the first two years to create a significant programming project. This is not dissimilar to what the course currently does, but the current model utlizes highly prescriptive milestones that are trivialized by generative AI usage.

Course Description

A study of concepts and techniques used to produce quality software programs. Object-oriented concepts, models, execution environments, design and testing techniques. Extensive application of these concepts and techniques to the development of non-trivial software programs.

Credit Hours

3 credits

Course Overview

This course is focused on helping you to learn the concepts and skills needed to develop high-quality software. Along the way you will have ample opportunities to practice these skills developing non-trivial software projects. These are not the “baby programs” of early CS coursework, but rather applications that could be used in a production environment.

Accordingly, our goal is not just to write software that compiles without errors, but to develop well-written and maintainable software. This goal demands extra attention to design, documentation, and testing. Additionally, we will explore some of the advanced features of programming languages and tools, as well as other professional tools like code repositories and diagramming software.

Course Goals and Learning Outcomes

By the end of this course, we expect each student to be able to:

  • Create class definitions that 1) utilize encapsulation to organize related data and behavior, 2) prevent uncontrolled internal state changes through information hiding, and 3) allow outside code controlled interactions through message passing.
  • Specify expected object behavior and verify it through creating and executing unit tests against a class definition.
  • Utilize polymorphism in the form of inheritance to minimize code duplication by moving shared fields and methods to a common ancestor.
  • Reason about dynamic dispatch to determine what version of a polymorphic function or method will be invoked at runtime.
  • Utilize industry standard developer tools to develop software reliably and efficiently.
  • Design, implement and test a project of your own design based on the principles covered in this course.

Confirmed Design Intent (not yet drafted into the schedule/assignments above)

Three threads (thread-code-comprehension.md, thread-boundaries-contracts.md, thread-sociotechnical.md) describe this course as a confirmed team-project capstone with a live-walkthrough/architecture-defense assessment — content that isn’t reflected anywhere in this page’s Topics, Schedule, or Assignments sections yet. Checked against resources/design-log.md: this is real, already-confirmed design intent (not an invented claim), just not yet written into this page. Recording it here so a future schedule/assignments draft starts from the actual decision rather than the current generic OOP-topics framing alone:

  • Team-based project, small teams with rotating scope — not the old model’s individually-assigned, highly-prescriptive milestones (which generative AI trivializes; see this page’s own opening note).
  • Project domain: the historical archive — a green-field build (explicitly not “Where Did They Go?”, which is a live external project used only as motivating context, not a build target).
  • Assessment leans on defended/oral components: a live walkthrough and architecture defense, not spec-compliance checklists — the AI-resistance mechanism for both the technical work and the team-collaboration claims.
  • Individual/collective split: every team produces something together, but every assessed artifact (including an individually-written responsibility retrospective) stays individually attributable.
  • Carries collaborative git/PR workflows, team-facing documentation, shared linting conventions, code review as an interpersonal/coordination skill (not just a technical check), and a light estimation/scoping touch.
  • Performance optimization against a real bottleneck — Big-O/complexity reasoning applied to the deployed project itself (“why is this slow”), not toy examples. Confirmed capstone touch for both the Algorithmic Thinking & Complexity thread and the Optimization Reasoning lens.
  • Harden the system before it goes live — a real, assessed security-hardening task, plus treating poorly-handled errors as attack surface. Confirmed capstone touch for the Trustworthy Computing lens.
